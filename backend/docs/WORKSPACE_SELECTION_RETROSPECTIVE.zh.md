# CVAgent 工作区选择对接复盘

## 结论

CVAgent 脱离 DSH 后，用户入口不应再暴露 `workspaceRoot`、`resumePath` 这类后端实现参数。用户只需要选择一个简历工作区；系统负责导入、识别简历源文件、建立长期会话绑定，并在后续请求中使用不透明的 `workspaceId`。

本次改造采用“选择目录 + CVAgent 管理副本”的首版方案：浏览器读取用户明确授权的工作区文件，上传到 CVAgent 的受管目录；Agent、模板、渲染、草稿、版本和会话都围绕受管工作区运行。原目录不会被静默覆盖，正式版本仍通过 CVAgent 的版本保存流程生成。

## 为什么不是继续让用户填写路径

旧实现把服务端的绝对路径直接暴露给 UI，适合开发调试，不适合作为独立产品入口：

- 用户要理解 Node 进程所在机器的文件系统，而不是理解产品概念；
- 路径输入容易产生跨平台、转义、权限和路径泄漏问题；
- `resumePath` 让用户承担了系统本应完成的文件识别工作；
- DSH 的宿主工作区概念已经不存在，继续沿用会让 CVAgent 看起来仍然依赖 DSH。

## 交互与数据边界

### 用户可见

- 选择工作区按钮；
- 当前工作区名称；
- 自动识别出的简历文件名；
- 最近使用的 CVAgent 工作区；
- 目标页数、模板和简历内容。

### 用户不可见

- 受管工作区绝对路径；
- `workspaceRoot`；
- `.cvagent` 元数据目录；
- 草稿、渲染产物、版本和会话的内部文件路径。

## 后端契约

新增工作区注册接口：

- `POST /api/workspaces/import`：接收浏览器选择目录后读取的文件清单，返回 `{ workspace: { id, name, resumeName } }`；
- `GET /api/workspaces`：列出最近工作区，只返回产品需要的元数据；
- `GET /api/workspace?workspaceId=...`：读取一个受管工作区的产品元数据。

业务接口优先接受 `workspaceId`：

- source、templates、previews、versions、sessions；
- agent bootstrap、agent run；
- 模板复制、模板保存和版本管理。

历史的 `workspaceRoot + resumePath` 契约暂时保留，作用仅是兼容已有测试、脚本和本地迁移；新 UI 不再产生这些字段。

## 工作区生命周期

```text
选择目录
  → 浏览器读取允许的文本/资源文件
  → CVAgent 创建受管工作区并自动识别 resume.md 或首个 Markdown
  → 返回 workspaceId
  → bootstrap 建立隔离草稿、模板上下文和渲染会话
  → Agent / 手动编辑 / 检查 / 测量 / finalize / 保存版本
```

工作区导入是幂等边界之外的显式动作：用户重新选择目录时创建新的受管工作区，不会覆盖既有工作区。这样能保留会话和版本历史，也避免一次误选破坏旧任务。

## 文件导入规则

- 允许简历、模板和材料常用的文本文件：Markdown、JSON、CSS、TXT、YAML、CSV；
- 允许简历渲染所需的常见图片资源；
- 忽略 `.git`、`node_modules`、`.cvagent` 和隐藏目录；
- 单个文本文件、图片文件和总导入体积均有上限；
- 所有相对路径在服务端重新校验，拒绝绝对路径和 `..` 穿越；
- 默认优先选择根目录 `resume.md`，否则选择根目录或浅层目录中的首个 Markdown 文件。

## 已知取舍与后续演进

浏览器的目录句柄不能直接变成 Node 服务端可用的绝对路径，所以首版采用“选择后导入受管副本”，而不是假装可以直接编辑用户原目录。后续若需要原地回写，可以增加桌面端桥接或显式导出/同步协议；这不应重新把绝对路径暴露给 Web UI。

## 验收标准

- 首次打开页面不出现工作区路径输入框或简历路径输入框；
- 用户完成一次目录选择后，能看到工作区名称和自动识别的简历文件名；
- 页面刷新后可以从最近工作区恢复选择；
- Agent bootstrap、模板加载、预览、版本和会话列表均只依赖 `workspaceId`；
- 现有路径兼容测试继续通过；
- 服务端不向新工作区 UI 返回受管工作区绝对路径；
- 浏览器端目录选择、后端导入和 Agent 主链路均有自动化验证。
