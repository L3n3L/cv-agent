# DeepAgent 开放工具面与 DSH 对接复盘

更新时间：2026-09-19

## 背景

之前的 `chat / read_only / production` 分流把“是否允许 Agent 看见工具”与“用户这句话是否需要工具”绑在了一起：普通聊天会被 middleware 清空工具，并设置 `toolChoice: none`。这不是 DeepAgent 的原生限制，而是 CVAgent 外层策略。结果是用户说“为什么会变成两页”“看一下现在是什么情况”这类自然语言时，Agent 可能完全无法读取当前工作区，表现为卡住或只能输出解释。

## 本次决策

保留执行模式这个概念，但只让它承担真正需要确定性的边界：

- `chat` 是开放工具面：DeepAgent 可以看到工作区、简历、模板、渲染和测量工具，由模型按意图决定是否调用；不强制调用，也不伪造调用。
- `read_only` 只在用户明确表达“只读、仅查看、不要修改、不修改”时启用，只暴露读取、检查和布局查询工具。
- `production` 保留完整工具面、`resume-production` Skill 和官方 `todoListMiddleware`，用于需要持续推进的简历生产任务。
- 工具的副作用、正式保存确认、当前 `renderId`、真实测量和完成门仍由工具与服务端确定性校验，不因开放工具面而放开。

这里的关键不是让每条消息都调用工具，而是不要在模型做判断前先把工具能力删掉。普通的“你好”仍然可以只回复一句话；“看下我的简历内容”则可以由 Agent 自己选择 `resume_read`，而不是靠关键词把工具权限切换出来。

## DeepAgent 原生对接方式

本次采用 DeepAgents 已提供的扩展点，不新增一套 CVAgent 自定义 Agent 循环：

1. `createDeepAgent` 继续负责模型—工具循环。
2. `skills` 在开放对话和生产模式挂载 DSH 对齐的 `resume-production` Skill，领域流程按需读取。
3. `todoListMiddleware` 仅生产模式启用，避免普通聊天出现计划卡片和伪进度。
4. `createMiddleware` 仅对显式只读请求过滤工具；开放对话原样透传 DeepAgent 的工具列表。
5. 服务器为开放对话和生产模式提供 Skill 文件，为只读模式不提供 Skill 文件，避免只读请求被生产流程诱导。

## 安全边界

开放工具面不等于开放所有副作用：

- `resume_write` 仍只写隔离草稿，不能覆盖源文件。
- `template_save`、`resume_save_version` 等正式持久化动作仍需要用户明确确认。
- `resume_finalize` 仍要求当前渲染、真实 A4 测量和完成条件满足。
- 工具失败、旧 `renderId`、真实测量缺失等状态必须原样反馈，Agent 不得用文字替代结果。
- 明确只读请求仍然是硬边界，不能因为 Skill 或模型判断而写入、渲染或保存。

## 验收矩阵

| 场景 | 预期 | 责任层 |
| --- | --- | --- |
| “你好” | 可以直接回复，不要求工具调用 | 模型 + 开放工具面 |
| “看下我的简历内容” | Agent 可自主调用真实读取工具并返回真实内容 | DeepAgent + domain tools |
| “只读检查，不要修改” | 不出现写入、渲染、模板保存工具 | execution middleware |
| “帮我把简历改成一页” | 可读取、修改隔离草稿、渲染、等待测量并继续推进 | Skill + tools + workflow |
| “保存正式版” | 未获明确确认时不得正式保存 | tool/server gate |

## 复盘结论

之前的问题不是 DeepAgent 不支持工具调用，而是 CVAgent 在模型之前做了过度的关键词权限裁剪。修复方向应优先回到 DeepAgent 的原生能力：工具面开放、领域规则进 Skill、复杂任务才启用规划、确定性副作用留在工具和服务端。以后新增限制必须回答两个问题：它是否是不可由模型判断的安全边界？是否已有工具级校验？如果两者都不是，就不应新增一层模式拦截。
